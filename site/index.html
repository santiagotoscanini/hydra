How it works

      
A plan from git, handed to process-compose.

      
Hydra runs no services and proxies no traffic. It decides what should run here, writes a normal process-compose file, and keeps that file up to date.

    

    

      

        
01

        
Diff

        
Lists the files that differ from where the branch left main, including uncommitted and new ones.

      

      

        
02

        
Match

        
A service runs here when one of those files matches its paths. Everything else stays on the baseline.

      

      

        
03

        
Wire

        
The worktree gets a slot. Ports shift by the slot, and env vars point at the local copy or the baseline's.

      

      

        
04

        
Watch

        
Every 2 seconds it plans again. Touch another service and it starts. Revert the change and it stops.

      

    

  






  

    

      
Configuration

      
Your process-compose file, plus a few fields.

      
Hydra reads x-hydra keys from the process-compose.yaml you already have. process-compose ignores them, so the same file keeps working for everyone who doesn't use Hydra.

      
    
        
  • paths say which files belong to a service.
    • 
        
  • upstreams say which env var points at which service.
    • 
        
  • shared keeps databases and tunnels on the baseline.
    • 
        
  • hydra takes the same arguments as process-compose.
    • 
      

      
All options

    

    

      
process-compose.yaml


x-hydra:
  base_ref: main
  slot_stride: 200       # slot N: port + N × 200

processes:
  db:
    command: docker compose up postgres
    x-hydra:
      shared: true       # always the baseline's

  api:
    command: go run ./services/api
    x-hydra:
      port: 8080
      port_env: API_PORT
      paths: ["services/api/**", "!**/*_test.go"]

  web:
    command: pnpm --filter web dev
    x-hydra:
      port: 3000
      paths: ["apps/web/**"]
      upstreams:
        API_URL: api     # local, else baseline


    

  






  

    

      
Stacked branches

      
A stack of branches runs as one stack.

      
When worktrees are stacked on each other, Hydra walks the chain down to main. Each branch is compared with its parent, so its diff holds only its own work, and each service runs from the worktree of the branch that changed it.

      
Run hydra in the top worktree. The watcher follows every worktree in the chain, so an agent editing the middle branch reaches the service through its own hot reload.

Details that matter

      
Built for agents working in parallel.

    

    

      

        
Never touches the baseline

        
Each worktree has its own process-compose socket. hydra down there stops that worktree and nothing else.

      

      

        
More than URLs

        
An upstream can be a queue name or a namespace, so a branch's jobs land on that branch's worker.

      

      

        
Out of git's way

        
The watcher reads git without taking its index lock, so it never collides with an agent's commits.
