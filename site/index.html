hydra
docs agents source

Ten agents, ten branches, one stack. Your laptop stops being the bottleneck.

Every agent works in a git worktree of its own, and needs the app running to check its change. Ten full stacks don't fit in memory and fight over the same ports. hydra, a small wrapper around process-compose, runs the full stack once, in your main checkout. In every worktree, hydra up starts only the services that branch changed, on their own ports, pointed at main's copy of everything else.

Needs git and process-compose, and Node.js for the dashboard. Built and used on macOS. For coding agents, it is also a plugin: an MCP server and skills.

What that looks like

Take a shop with a frontend, an API, a worker and a database. Main runs all four. Two agents work in two worktrees, and each worktree runs only what its agent changed.

  • runs in this worktree
  • main's copy, answering on this worktree's port
  • main's: the worktree uses main's copy

What you add to process-compose.yaml

hydra learns all of that from the file you already have. You add an x-hydra block to the processes it should know about. process-compose ignores keys it doesn't know, so the file keeps working for anyone who runs it without hydra.

process-compose.yaml+the lines you add
version: "0.5"

x-hydra:
  slot_stride: 200

slot_stride is how far apart worktrees sit. The first one listens on every port + 200, the second on + 400.

Worktrees are compared with the repository's default branch, which hydra reads from git.

processes:
  db:
    command: docker compose up postgres
    x-hydra:
      shared: true

shared means there is only ever main's copy. Use it for databases, Docker and tunnels.

A process with no x-hydra block is treated the same way.

With many worktrees, pool: 6432 puts PgBouncer in front of it.

  api:
    command: go run ./services/api
    x-hydra:
      port: 8080
      port_env: API_PORT
      paths: ["services/api/**", "!**/*_test.go"]

paths are the files that mean "this branch changed the api". A leading ! excludes.

port is where main's copy listens. A worktree's copy is told its own port through port_env.

  web:
    command: pnpm --filter web dev
    depends_on:
      api: { condition: process_started }
    x-hydra:
      port: 3000
      paths: ["apps/web/**"]
      routed: node
      upstreams:
        API_URL: api

upstreams maps an environment variable to the service it points at.

In a worktree, API_URL is that worktree's api if it runs there, and main's otherwise.

routed is step 4 above: main's copy serves the worktrees that didn't change it. More below.

Every option, with defaults, is in the docs.

How it decides

Those paths are all hydra goes by. A service runs in a worktree when a file that differs from where the branch left main matches them. Committed, staged, unstaged and new files count; git-ignored files don't. It is the list these two commands print:

$ git diff --name-only $(git merge-base HEAD main origin/main)
$ git ls-files --others --exclude-standard

With that list, hydra up in a worktree:

  1. Picks the services whose paths match.
  2. Takes a slot for the worktree, which decides its ports.
  3. Checks that main's stack is up and in step with the branch, and stops with the fix if it isn't.
  4. Writes .process-compose/hydra.yaml: those services only, with their ports and upstreams set.
  5. Starts process-compose on it, on a socket of its own. hydra down in a worktree can't stop main's stack.

So what runs is an ordinary process-compose project with a few environment variables set. hydra doesn't sit between your services, with one exception, described below.

When things change

An agent keeps editing after the stack starts, so the list is never final. The generated file has one extra process, hydra-watch, which asks git the same question every two seconds. A service can only move in two directions, and that is all the watcher does:

uses main's copy
a changed file matches its paths
the last such change is reverted
runs here

Services that point at it are restarted with the new address. Further edits to a service that already runs here are left to its own reload, like next dev or air.

It asks git rather than watching files because only git knows whether a file still differs from main: a revert has to stop the service, and a write to node_modules must not start one. It reads without taking git's index lock, so it never gets in the way of an agent's commit.

Stacked branches work too: each branch is compared with its parent, and each service runs from the worktree of the branch that changed it. A PR stack checked out at its top only still counts its lower branches: they are shown, and updated with their parents, without a checkout. How a stack is found.

A worktree that is removed takes its stack with it. The watcher notices, stops everything that ran there and deletes what git couldn't, and the ports go to the next worktree only after that. Stopping and cleaning up.

Main moves when you say so

Everything so far leans on main: every worktree calls main's running copies of what it didn't change. So main has to stand still until you decide to move it, because a worktree from last week calling today's API can fail for reasons that have nothing to do with its branch. Turn off anything that pulls main by itself, and let one command move everything together:

$ hydra update
main  ~/code/shop  moved 9a782732a → 66b4f7b80 (4 commits)

main's stack
  migrate  ran again  db/migrations/0042_orders.sql  done in 6s
  api      restarted  services/api/handler.go        ready in 9s

worktrees
  shop-cart      cart      main merged in (4 commits); restarted there: web
  shop-checkout  checkout  CONFLICTS with main in 1 file (4 commits behind)
  1. It pulls main, fast-forward only.
  2. It runs the jobs again and restarts the services the pull touched, in order, waiting for each. A migration that fails stops it before the API restarts.
  3. It merges main into every worktree where the merge is clean. Conflicts and uncommitted work are left alone and listed.

Between updates, hydra keeps watch. hydra up won't start a worktree whose branch and main disagree on a service it takes from main, or whose main isn't running. hydra status says what is wrong and which command fixes it. Everything it does and sees, in every checkout, goes into one journal: hydra log reads it, hydra report turns it into one file to send when you need help.

One frontend for all of them

Back to step 4: api-paging changed only the API, yet its agent opened a page. Without help it couldn't, since the frontend runs in main and calls main's API. A dev server per worktree would fix that, and it is the most expensive process in the stack. So a service marked routed keeps one copy, in main, which serves every worktree that left it alone. This is where hydra does sit in the path of a request:

you open  localhost:3400         slot 2's port for web. hydra's router answers,
                                 marks the request "worktree 2", passes it on
          main's web  :3000      renders the page; its API call keeps the mark
          hydra's router         reads the mark
          slot 2's api  :8480    or main's api, if slot 2 runs none

The mark is a header. Chrome doesn't send it: the router adds it, because a request on port 3400 can only be for slot 2. The frontend has to copy it onto the calls it makes, and routed: node loads a small script into the Node process that does that, so the app isn't changed.

Three rules keep this from testing the wrong code without telling you:

  1. The router checks that the mark really comes out the other side before a worktree may use main's copy.
  2. A call that can't be routed, such as a queue name read once at start, makes the frontend run in the worktree after all.
  3. If a worktree's API is down, its calls fail. They never fall back to main's API.

Ports move with the slot, so a name is easier to keep: with hosts: 3900 on web, api-paging.localhost:3900 is always that worktree's frontend, whichever copy serves it, and localhost:3900 is main's.

The same router moves the one public tunnel for webhooks (cloudflared, ngrok): hydra tunnel take in a worktree, and Twilio's or Stripe's callbacks reach that worktree's API until hydra tunnel release or hydra down. When its API is down they get a 502 that says so, never main's answer.

All of it on one screen

    
Every command so far acts on one checkout. With a few agents at work you want to see all of them at once, so type hydra on its own. It opens a dashboard of main and every worktree, named by branch, as a tree of branches with each stacked one under its parent (a PR stack's branches with no worktree included): whether its stack is up, how it stands against its parent (a branch on one that is behind is out of date too, and the row where it starts stands out), its pull request in a few characters (a worktree whose PR is already merged says so, and the header counts them), and for the one you pick, in a panel below, what runs there and why: its PR, its chain up to main, each service with the files that made it run there, what it takes from main, and what is wrong with the fix.

Each key runs the command you would type, in the checkout you picked: u is hydra up -D, m merges its parent into that worktree alone (hydra update --here), f runs the fix, p opens the PR, and ⏎ opens the stack in process-compose; F10, then Yes, brings you back with the stack still running. Whatever stops a stack or moves a branch asks first, and q leaves every stack running.

    
Agents don't need it. It reads hydra status --json, which they can read too, so what you see and what they see is the same.

Built for agents in every worktree

    
hydra exists for five agents working on five branches at once. Given a shell, an agent gets a dev stack wrong in ways that cost you: it starts process-compose by hand on main's ports, stops main's stack because its own "looks broken", resets the database everyone uses. So hydra gives it tools instead. hydra mcp is an MCP server with status, up, wait, logs, restart and down, all for the agent's own worktree. Asked to change main's stack, they refuse and tell the agent to ask you.

    
The repository is a plugin marketplace. One install gives Claude Code the server and three skills:

  

  


/plugin marketplace add santiagotoscanini/hydra
/plugin install hydra@hydra


  

  

    
    
      
  • hydra: running the app in a worktree, its ports and logs, and what to do with every ✗ hydra prints: which fixes are the agent's, and which are yours.
    • 
      
  • hydra-setup: "set hydra up here". The agent reads your services, writes the x-hydra blocks, and checks them with hydra plan in a throwaway worktree.
    • 
      
  • hydra-update-all: pull main, then merge it into every worktree and stacked branch, parents first, resolving the conflicts. It shows you the plan and waits for your yes; the dashboard follows along.
    • 
    

    
Codex: codex plugin marketplace add santiagotoscanini/hydra. Any agent that reads skills: npx skills add santiagotoscanini/hydra.
