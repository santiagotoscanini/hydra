hydra
docs source

Every worktree gets a running stack. Only the services it changed actually start.

hydra is a small wrapper around process-compose. Your main checkout runs the full stack, once. In every other git worktree, hydra starts the services that branch touched, on their own ports, and points them at main's copy of everything else.

Needs git and process-compose. Built and used on macOS.

What that looks like with agents at work

Rows are checkouts and columns are services. A lit cell is a process running in that checkout. A dot means the checkout uses main's copy. A ring is main's frontend answering on that checkout's own port, with its API calls sent to that checkout.

Not a recording. The cells follow the rules hydra applies, and the log lines are the ones hydra-watch prints.

What you add to process-compose.yaml

hydra reads x-hydra keys from the file you already have. process-compose ignores keys it doesn't know, so the file keeps working for anyone who runs it without hydra.

process-compose.yaml+the lines you add
version: "0.5"

x-hydra:
  slot_stride: 200

slot_stride is how far apart worktrees sit. The first one listens on every port + 200, the second on + 400.

Worktrees are compared with the repository's default branch, which hydra reads from git.

processes:
  db:
    command: docker compose up postgres
    x-hydra:
      shared: true

shared means there is only ever main's copy. Use it for databases, Docker and tunnels.

A process with no x-hydra block is treated the same way.

  api:
    command: go run ./services/api
    x-hydra:
      port: 8080
      port_env: API_PORT
      paths: ["services/api/**", "!**/*_test.go"]

paths are the files that mean "this branch changed the api". A leading ! excludes.

port is where main's copy listens. A worktree's copy is told its own port through port_env.

  web:
    command: pnpm --filter web dev
    depends_on:
      api: { condition: process_started }
    x-hydra:
      port: 3000
      paths: ["apps/web/**"]
      routed: node
      upstreams:
        API_URL: api

upstreams maps an environment variable to the service it points at.

In a worktree, API_URL is that worktree's api if it runs there, and main's otherwise.

routed lets main's copy serve the worktrees that didn't change it. More below.

Every option, with defaults, is in the docs.

How it decides

A service runs in a worktree when a file that differs from where the branch left main matches its paths. Committed, staged, unstaged and new files count. Git-ignored files don't.

$ git diff --name-only $(git merge-base HEAD main origin/main)
$ git ls-files --others --exclude-standard

With that list, hydra in a worktree:

  1. Picks the services whose paths match.
  2. Takes a slot for the worktree, which decides its ports.
  3. Checks that main's stack is up and in step with the branch, and stops with the fix if it isn't.
  4. Writes .process-compose/hydra.yaml: those services only, with their ports and upstreams set.
  5. Starts process-compose on it, on a socket of its own. hydra down in a worktree can't stop main's stack.

hydra writes a normal process-compose file and sets environment variables. It sits in the path of a request in one case only, described below.

When things change

The generated file has one extra process, hydra-watch. Every 2 seconds it asks git the same question again. A service can move in two directions, and that is all the watcher does:

uses main's copy
a changed file matches its paths
the last such change is reverted
runs here

Services that point at it are restarted with the new address. Further edits to a service that already runs here are left to its own reload, like next dev or air.

It asks git instead of watching the file system because only git knows whether a file differs from main. A revert has to stop the service, and node_modules must not start one. It reads git without taking the index lock, so it stays out of the way of an agent's commits.

Stacked branches work too: each branch is compared with its parent, and each service runs from the worktree of the branch that changed it. How a stack is found.

A worktree that is removed takes its stack with it. The watcher notices that its directory is gone and stops everything that ran there, and the ports go to the next worktree only after that. Stopping and cleaning up.

Main moves when you say so

Every worktree takes main's running copies, so main has to stay still until you decide to update it. A worktree from last week calling today's API can fail for reasons that have nothing to do with its branch. So turn off anything that pulls main by itself, and let one command move everything together:

$ hydra update
main  ~/code/shop  moved 9a782732a → 66b4f7b80 (4 commits)

main's stack
  migrate  ran again  db/migrations/0042_orders.sql  done in 6s
  api      restarted  services/api/handler.go        ready in 9s

worktrees
  shop-cart      cart      main merged in (4 commits); restarted there: web
  shop-checkout  checkout  CONFLICTS with main in 1 file (4 commits behind)
  1. It pulls main, fast-forward only.
  2. It runs the jobs again and restarts the services the pull touched, in order, waiting for each. A migration that fails stops it before the API restarts.
  3. It merges main into every worktree where the merge is clean. Conflicts and uncommitted work are left alone and listed.

In between, hydra keeps watch. hydra up won't start a worktree whose branch and main disagree on a service it takes from main, or whose main isn't running. hydra status says what is wrong and which command fixes it, and hydra ui shows the same for every worktree as a page in your browser.

One frontend for all of them

A branch that only changed the API has no page to open: the frontend runs in main and calls main's API. A second dev server per worktree would fix that, and it is the most expensive process in the stack. So a service marked routed keeps a single copy, in main, that serves every worktree which left it alone.

you open  localhost:3400         slot 2's port for web. hydra's router answers,
                                 marks the request "worktree 2", passes it on
          main's web  :3000      renders the page; its API call keeps the mark
          hydra's router         reads the mark
          slot 2's api  :8480    or main's api, if slot 2 runs none

The mark is a header. Chrome doesn't send it: the router adds it, because a request on port 3400 can only be for slot 2. The frontend has to copy it onto the calls it makes, and routed: node loads a small script into the Node process that does that, so the app isn't changed.

Three rules keep this from testing the wrong code without telling you:

  1. The router checks that the mark really comes out the other side before a worktree may use main's copy.
  2. A call that can't be routed, such as a queue name read once at start, makes the frontend run in the worktree after all.
  3. If a worktree's API is down, its calls fail. They never fall back to main's API.
